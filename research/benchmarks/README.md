# Benchmark design

The benchmark evaluates runtime policy enforcement at the agent-to-tool boundary. It is intentionally deterministic: scenarios are synthesized tool calls rather than LLM-generated traces.

## Sources

- `seed`: manually specified, policy-independent scenarios used to define the initial task space.
- `mutation`: programmatically generated variants of seed requests, such as amount, path, action, or identity perturbations.
- `held_out`: scenarios reserved from development and used only for final evaluation.
- `independent_review`: scenarios or labels independently reviewed by someone not responsible for the corresponding policy implementation.

Every expected label must be determined from the declared policy/task specification rather than copied from Aegis output.

## Coverage

The current policy surface is intentionally narrow and covers:

- identity authorization;
- tool authorization;
- action authorization;
- payment parameter constraints;
- HR file-path constraints.

The benchmark therefore should be described as a **deterministic policy-enforcement benchmark**, not a comprehensive security or prompt-injection benchmark.

## Reproducibility requirements

Every frozen benchmark must be content-hashed. Experiment artifacts should record:

- benchmark version;
- benchmark SHA-256;
- source Git commit;
- policy version;
- experiment configuration;
- repetition count;
- raw per-scenario records.

Before reporting results, verify that every system used the same benchmark hash and scenario count and that every repetition is fully classified.

## Statistical interpretation

A repetition is one complete pass over the frozen benchmark. Repetitions are useful for measuring reproducibility and latency variation, but repeating the same deterministic scenarios does **not** turn them into independent security samples.

Security metrics should therefore be reported with their exact scenario denominator. Latency confidence intervals may use repetition-level observations.

## Research limitations

A benchmark can be internally reproducible and still have limited external validity. The current suite is derived from a small policy surface and deterministic scenario families. It does not establish robustness to arbitrary unseen attacks, prompt injection, model misalignment, delegation chains, temporal policy changes, or cross-system state.

A paper-quality follow-up should add a held-out set created and independently reviewed without using Aegis implementation behavior as the labeling oracle.
