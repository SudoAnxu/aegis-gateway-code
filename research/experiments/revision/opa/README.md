# OPA/Rego Static Policy Comparison

**Generated:** Revision phase.

## Purpose

Compare Aegis's policy enforcement against an independently implemented OPA/Rego policy that encodes the same static (stateless) policy rules. This tests whether the Aegis implementation is consistent with an industry-standard policy-as-code approach on the static policy dimensions.

## Scope

This comparison covers **static policy enforcement only**:

- Agent/tool/action authorization
- Parameter constraints (amount bounds, currency whitelist)
- Path prefix constraints

This comparison does **NOT** cover:

- Stateful semantics (state transitions, duplicate detection, precondition checks)
- Identity verification (unknown-agent rejection)
- Request validation (malformed request handling)
- Type checking (type confusion detection)

These limitations are documented because OPA/Rego evaluates declarative input without maintaining state. A stateful comparison would require a different architecture (e.g., OPA with external data or a stateful plugin).

## Policy Implementation

The Rego policy (`policy.rego`) implements:

1. **Finance agent authorization:** payments tool, create/refund actions, amount [0, 5000], currencies {USD, EUR}
2. **HR agent authorization:** files tool, read action, path prefix `/hr-docs/`
3. **Default deny:** everything else is denied

## Input Schema

Each OPA input is a JSON object:

```json
{
  "agent": "finance-agent",
  "tool": "payments",
  "action": "create",
  "parameters": {
    "amount": 1250,
    "currency": "USD"
  },
  "history": []
}
```

The `history` field is accepted but ignored by the OPA policy (static comparison).

## Case Translation

Cases from the Aegis benchmark are translated to OPA input format using a deterministic script (`run_opa.py`). The translation maps:

- `agent` → `input.agent`
- `tool` → `input.tool`
- `action` → `input.action`
- `parameters` → `input.parameters`
- `expected` → ground truth label

The translation was generated by the revision-phase script, not by a separate human reviewer.


## Limitations

1. **Static-only:** The OPA policy does not implement stateful checks. Any case requiring state history evaluation is excluded.
2. **Single implementation:** This is one Rego encoding of the policy. Different Rego implementations could produce different results.
3. **No identity check:** The OPA policy does not check for unknown-agent rejection (this is handled differently in Aegis).
4. **No type checking:** The OPA policy does not check parameter types (string vs number).
5. **No malformed detection:** The OPA policy does not check for missing or malformed parameters.
